# CareerPilot 求职准备 Agent

CS353FZ 五人团队项目。面向大学生实习求职，结合个人经历、目标岗位和检索到的知识资料，提供有依据的岗位分析、准备计划和模拟面试。

当前阶段：开发骨架与 B 的本地认证实现。已有 React/TypeScript 页面、FastAPI 路由与类型契约、本地依赖 Compose 和 PR 检查；已接通 MongoDB 种子账号、登录和本人资料接口。上传、JD、RAG 与 Agent 业务仍待实现。页面样例不代表真实分析结果。

## 从这里开始

1. 按 [本地启动指南](dev/09-本地开发启动-local-setup.md) 安装锁定依赖，启动前后端；前端默认地址为 `http://127.0.0.1:5173`，API 文档为 `http://127.0.0.1:8000/docs`。
2. 阅读 [M1 开工计划](dev/08-M1开工计划-kickoff-plan.md)，使用 [合成样例](examples/README.md) 对齐契约；只索引原始简历和项目说明。
3. 认领下方任务，在已有模块上开发。登录和本人资料接口已实现，其余业务接口当前返回 `501 NOT_IMPLEMENTED`，完成模块后再接真实服务联调。

**M1 只做：文本资料上传 → JD 导入 → 向量检索 → 逐项分析 → 原文引用展示。** 准备计划、模拟面试和云端部署不作为本轮开发前置条件。

## 技术与部署方案

| 层次 | 方案 | 在项目中的作用 |
| --- | --- | --- |
| 前端 | React + TypeScript + SSE | 页面交互、带出处的分析展示及实时执行进度 |
| 业务后端 | FastAPI + Pydantic | API、鉴权、输入输出校验及任务/计划管理 |
| Agent | LangGraph + Tool Calling + 持久化状态 | 岗位拆解、证据匹配、资料追问、计划确认与恢复 |
| RAG | Qdrant + 混合检索 + Rerank | 从个人经历和公共知识中检索证据；先评测向量基线再引入增强策略 |
| 业务存储 | 托管 MongoDB | 用户、JD、资料版本、任务、计划与面试记录 |
| 后台任务 | Celery + Redis | 分发解析、索引与 Agent 执行任务，业务状态保存在 MongoDB |
| 原始文件 | 阿里云 OSS 私有存储 | 简历、项目说明和版本化解析文本 |
| 云端运行 | 阿里云 ECS + Docker Compose + Nginx/HTTPS | 在云服务器运行前端、API、Worker、Redis 和 Qdrant |
| 工程交付 | GitHub Actions 检查/构建，负责人确认后发布 | 已添加 PR 检查与本地依赖连接验证；云端镜像发布和部署尚未实现 |

本地开发联调完成后，应用最终部署到云服务器。Docker Compose 在本地和 ECS 上管理容器；GitHub Actions 负责检查与构建，正式发布由负责人手动触发。模型、Embedding 和 Rerank 初期通过 API 调用，ECS 主要运行应用和检索服务。

Qdrant 保存可重建的向量索引并查找相关文档片段；MongoDB 保存权威业务数据与来源记录，OSS 保存原始文件。完整的入库、检索和部署关系见 [技术架构](dev/02-技术架构-architecture.md)。

## 产品范围

用户上传简历及项目说明，导入目标岗位描述（JD）。系统提取岗位要求，检索个人经历与知识库，展示匹配依据及待补充信息，生成准备计划。用户确认后，计划保存为可跟踪任务。基础闭环完成后，再加入针对个人项目和岗位要求的模拟面试。

- P0：个人资料管理、JD 导入、带出处的匹配分析、准备计划预览与确认保存。
- P1：任务进度跟踪、文本模拟面试与反馈。
- 本期不包含：自动投递、全网岗位爬虫、语音面试、视频情绪分析和多 Agent 集群。
- 未检索到经历时，标记“现有资料未体现”，并允许用户补充；不得编造经历、证书、项目结果或面试表现。

P0/P1 表示最终交付优先级；实现顺序另按里程碑划分：

| 里程碑 | 本阶段交付 | 阶段边界 |
| --- | --- | --- |
| M1 最小流程 | Markdown/TXT 上传、JD 导入、真实向量检索、匹配分析和引用展示 | 本地合成数据；最小任务分发与轮询；缺失信息记入结果，不暂停追问 |
| M2 完善 P0 | PDF、资料更新/删除、准备计划确认、SSE、状态恢复与队列可靠性，比较混合检索/Rerank | 负责人确认验收后准备云端发布 |
| M3 P1 扩展 | 任务进度看板、文本模拟面试与反馈 | 按团队进度扩展，不阻塞 M1 |

本页技术栈描述总体目标，M1 的必要组件、接口和数据集合以 [开工计划](dev/08-M1开工计划-kickoff-plan.md) 为准。

## 模块协作

```text
A 前端 → B 业务 API → Celery/Redis → D LangGraph → C RAG/Qdrant
                ↘ MongoDB 业务记录 / 私有 OSS 原文件
B 资料上传 → 队列 → C 解析及建索引 → 就绪后供 D 调用
Worker 持久化业务事件 → B SSE → A 展示进度及补充信息请求
D 生成计划草稿并暂停 → A 确认 → B 保存正式计划并恢复执行
```

1. 负责人先确定需求边界、数据模型与 API 草案。
2. A、B 根据同一份 API 契约开发；C、D 根据同一份内部工具契约开发。
3. 第一条联调链路：简历上传 → 资料就绪 → JD 导入 → 分析任务 → 引用展示。
4. 第二条链路：生成计划 → 用户确认 → 保存任务 → 修改任务状态。
5. 最后扩展文本面试，由负责人执行整体验收与部署。

模块发生变更时，同时维护实现、接口文档和对应 Issue。报告按实际贡献分写：A 负责交互设计，B 负责业务实现，C 负责 RAG 方法，D 负责 Agent 流程，负责人负责总体设计、评测整合和交付。

## Git 协作要求

**先建 Issue，再开工作分支；禁止直接向 `main` 提交或推送，所有改动通过关联 Issue 的 PR 合入。**

- `main` 保存经审查的稳定版本；`dev/` 是文档目录，不是集成分支。
- 团队分支示例：`feat/42-jd-import`、`fix/43-citation-location`、`docs/44-api-spec`。
- Commit 格式：`type(scope): 简明描述`；正文使用 `Refs #<Issue编号>` 关联任务。
- PR 描述使用 `Closes #<Issue编号>` 关联本次完成的 Issue；部分完成使用 `Refs #<Issue编号>`。
- 至少一位其他成员审查，负责人或约定维护者合并；不得自行批准自己的 PR。
- 完整要求与命令示例见 [Git 协作规范](dev/07-Git协作规范-git-workflow.md)。
